## 3. O que mudou de status nesta revisão (e por quê)

### 3.1 ⚠️ Containers `comfyui`+`mcp` separados: código pronto, nunca implantado

Eu tinha marcado esta tarefa como concluída antes. **Estava errado.** O que
de fato existe:

- `docker/docker-compose.yml` declara 2 serviços (`comfyui`, `mcp`) — **código correto**.
- `docker/Dockerfile.python` (imagem Python enxuta para o `mcp`) — **existe, nunca foi construído** (`docker images` não lista `minimax-python:local`).
- O container `minimax-comfyui` que está de pé agora (`Up 40+ horas`) é o
  **container antigo**, de antes da separação — rodando a imagem monolítica
  de 36 GB, não a nova arquitetura.

**Por que os testes passaram mesmo assim:** `/workspace` é bind-mount do
repositório no host. O container antigo está executando o `server.py`
**atual** (12 tools) porque o código é lido direto do disco, não da imagem
— só dependências novas exigiriam rebuild, e a separação só *removeu*
dependências. É por isso que `health_check`, `queue_status` e os renders
reais da CI (ver §6) funcionaram sem eu notar o problema antes.

**O que falta de verdade:**
```bash
docker compose --project-directory /home/leodg/tools-local/minimax-video-factory \
  --env-file /home/leodg/tools-local/minimax-video-factory/.env \
  -f /home/leodg/tools-local/minimax-video-factory/docker/docker-compose.yml \
  build
docker compose ... up -d
```
Comando já identificado, bloqueado para execução direta nesta sessão pelo
classificador de permissão (`docker compose` exige confirmação manual do
usuário). **Isto é a única pendência operacional real** deste repo.

### 3.2 Task #8 ("4 lugares por tool MCP") — já estava feita, confirmado

Verificado de novo: `scripts/command_docs/catalog.py` tem só as 12 tools de
vídeo, `tests/unit_registry.py` espera 12, `README.md` reflete 12, e
`scripts/generate_commands.py` foi rodado (os `.md` em `.opencode/command/`
e `.claude/commands/` batem 1:1 com as tools). Para o `insta_kb`: não existe
gerador de slash command nesse projeto (MCP + REST apenas), então o item
não se aplica — confirmado, não é uma lacuna.

### 3.3 As "8 correções" que eu temi estarem faltando no insta_kb — já estavam lá

Uma investigação no meio da sessão (comparando o histórico do `main` do
video-factory contra o ponto em que o worktree de separação divergiu)
sugeria que ~8 commits de correção real (heartbeat AMQP, carrossel misto,
mídia degradada, etc.) tinham ficado de fora da migração. **Verificação
código-a-código contra o `insta_kb` mostrou que as 8 já estavam presentes**
— a migração original partiu de um checkout tardio do `main`, não da base
antiga do worktree. Nenhuma delas precisou ser re-portada; só reforcei a
cobertura de teste (28 testes novos) para esse comportamento, que existia
mas não tinha teste dedicado.

## 4. Bugs reais encontrados e corrigidos nesta revisão

### 4.1 `../CLAUDE.md` quebrando o build `--strict` do MkDocs em CI

**Onde:** `docs/HANDOFF.md`, `docs/PROMPT_DESENHO_COM_FALA.md`.
**Sintoma:** o workflow `Docs` falhava em CI de verdade (`Aborted with 2
warnings in strict mode!`) — eu tinha identificado esse link quebrado numa
passada anterior da sessão e **deliberadamente deixei fora de escopo**,
avaliando como "não bloqueia nada". Estava errado: bloqueava o CI real.
**Corrigido:** trocado o link relativo por URL absoluta do GitHub (resolve
nos dois contextos). Commit `e1066ae`, CI `Docs` verde depois.

### 4.2 `bandit` com 2 achados medium passando localmente, falhando em CI

**Onde:** `insta_kb/src/core/settings/config.py` — `MCP_HOST`/`API_HOST =
"0.0.0.0"` (B104).
**Sintoma:** eu vinha tratando esses dois achados como "aceitos" ao longo
de toda a sessão (bind intencional dentro de container) só lendo o resumo
(`Medium: 2`) — **nunca conferi o código de saída**. `bandit` sem
`--exit-zero`/filtro de severidade sai com código 1 para qualquer achado,
mesmo medium. O workflow de CI que acabei de criar rodou de verdade e
falhou nos dois, nas duas branches (`main` e `dev`).
**Corrigido:** `# nosec B104` com comentário explicando a razão (interface
do container, não do host; a porta só fica exposta via o mapeamento do
compose, que já restringe a `127.0.0.1`). Commit `1c75d77`, CI verde depois
nas duas branches.

**Lição que vale registrar:** "rodar o comando e ler o resumo" não é o
mesmo que "verificar que passa" — o código de saída é o que importa, e só
apareceu porque desta vez havia um CI de verdade cobrando isso. Os dois
achados sempre estiveram lá, só nunca tinham sido testados por um pipeline
que realmente falha.

## 5. CI/CD no insta_kb — avaliação e implementação

**Fazia sentido?** Sim, e sem ressalvas: a suíte inteira (164 testes) roda
sobre mocks — nenhum teste toca Postgres, RabbitMQ, Ollama ou
faster-whisper de verdade. Não precisa de GPU nem de self-hosted runner,
ao contrário do video-factory (que precisa renderizar de verdade). Um
runner cloud comum (`ubuntu-latest`) basta.

**Implementado:** `.github/workflows/ci.yml` — `ruff check`, `ruff format
--check`, `pyright` (strict), `bandit`, `pip-audit`, `pytest`. Roda em
push/PR para `main` e `dev`. São exatamente os mesmos checks que o
`pre-commit` já roda localmente — a diferença é que agora rodam também
antes de qualquer merge, não dependem de ninguém ter instalado o hook.

**Resultado real:** a primeira execução **falhou** (o bug §4.2) — prova de
que o CI está fazendo o trabalho que deveria fazer, não um teatro verde. A
segunda, depois do fix, passou nas duas branches.

**Não implementado, por decisão consciente:** workflow de docs (mkdocs) —
o insta_kb não tem site de documentação ainda, só o README; não há nada
para publicar. Se um dia o projeto crescer a ponto de precisar de um
(como o video-factory tem), replicar o padrão `docs.yml` de lá é direto.
